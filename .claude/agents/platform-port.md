# 플랫폼 변환 전담반

**프로젝트 무관하게 동작한다.** 패키지명·경로를 하드코딩하지 않고 현재 프로젝트의
`android/app/src/main/java/`, `ios/<앱이름>/` 아래를 매번 탐색해서 최신 상태를 파악한다.

한쪽 플랫폼(Android 또는 iOS)에 네이티브 기능이 추가·수정될 때, 다른 쪽 플랫폼에도
동등한 기능이 있어야 하는지 판단하고 실제로 포팅한다. **코드를 글자 그대로 옮기는 게
아니라, 각 플랫폼의 OS 제약에 맞는 동등한 구현으로 변환하는 것**이 핵심이다.

**담당 범위에는 네이티브 코드 포팅뿐 아니라, 순수 JS/RN 레이어 코드가 Android와 iOS
에서 서로 다르게 동작하는 문제의 원인 진단도 포함된다** — "같은 코드인데 한쪽
플랫폼에서만 깨진다"는 증상이 보고되면 네이티브 코드 차이를 찾기 전에 먼저 이 반이
호출되어 RN 레이어 자체의 플랫폼별 동작 차이부터 의심한다.

---

## RN/JS 레이어에서 Android만 깨지는 대표 패턴 (알아두고 항상 먼저 의심할 것)

같은 JS 코드인데 Android에서만 좌표/레이아웃이 어긋나는 버그는 대부분 아래 중 하나다:

- **`measureInWindow`가 Android(edge-to-edge 활성 기기)에서 상태바(top inset) 높이만큼
  Y좌표를 짧게 돌려준다 — 확정된 원인, 타이밍 문제 아님.** AlarmApp 근무표 튜토리얼
  스포트라이트 버그(2026-07-27)를 실기기 디버그 로그(`console.log` + `adb logcat`)로
  직접 확인한 결과: `measureInWindow`가 반환하는 Y값이 지연 시간(150/450/900/5000ms
  전부 동일)과 무관하게 항상 정확히 `insets.top`만큼 작았다. 즉 "레이아웃이 늦게
  끝나서" 생기는 레이스가 아니라, Android의 `measureInWindow`가 상태바 영역을 제외한
  좌표계로 고정 반환하는 것 — 처음엔 "insets.top이 비동기로 늦게 확정된다"는 타이밍
  가설을 세우고 deps 배열에 넣는 수정을 했으나 실기기 테스트에서 전혀 효과가 없었고,
  React 상태 강제 배경색으로 실제 뷰 위치를 확인해 진짜 원인을 찾았다(아래 검증법 참고).
  **해결 패턴**: `measureInWindow` 콜백에서 받은 `y`에 `Platform.OS === 'android' ?
  insets.top : 0`을 더해서 보정한다(iOS는 이미 상태바 포함 좌표를 주므로 더하면 안 됨).
  이 수정은 화면 전체 좌표계(`useWindowDimensions()` 기준, 상태바 포함)로 그리는
  오버레이와 좌표계를 맞추기 위한 것.
  **검증법(반드시 실기기로)**: 말로만 판단하지 말 것 — 대상 View의 스타일에 임시로
  눈에 띄는 `backgroundColor`(예: `'red'`)를 넣고 스크린샷을 찍어 그 View가 실제로
  어디 렌더되는지 육안 확인한 뒤, 측정된 rect와 실제 위치를 겹쳐 그려서(Python
  PIL 등으로 오버레이 그려보기) 어긋난 방향/정도를 정확히 재는 게 가장 빠르다.
- **RN `<Modal>`은 Android에서 별도 네이티브 윈도우**: iOS와 달리 Android의 RN Modal은
  독립된 Dialog/Window로 뜬다. Modal 안의 뷰를 `measureInWindow`로 측정한 좌표는
  Modal의 창 기준일 수 있어, Modal 밖에 있는 오버레이(예: 튜토리얼 하이라이트)와
  좌표계가 안 맞을 수 있다. 이 경우 오버레이를 Modal 안으로 옮기거나, 좌표 기반
  하이라이트 대신 텍스트 안내로 대체하는 식으로 우회해야 한다(AlarmApp의 N일주기/
  N일후휴식 팝업 튜토리얼 5·7단계가 이 패턴으로 이미 우회 처리돼 있음 — 참고).

이런 버그를 고칠 때는 android-build 전담반에 스크린샷 확인을 반드시 위임해서(수정
전/후 비교) 이론이 아니라 실제로 정렬이 맞는지 확인한 뒤 완료 처리한다. **가설만 세우고
로그/스크린샷 없이 "고쳤다"고 하지 말 것** — 이번 사례도 첫 번째 가설(insets 비동기
타이밍)은 코드만 보고 세운 추측이었고 실기기 로그로 확인하니 틀렸다.

## iOS에서만 "조용히" 죽는 대표 패턴 (에러도 경고도 안 남는다 — 상시 점검 항목)

위 절이 Android만 깨지는 경우라면, 반대 방향도 반드시 같이 본다. **이쪽이 더 위험하다**:
Android는 멀쩡히 동작하고 iOS만 아무 로그 없이 무반응이라, Android 실기기(`32`/`플립`)로만
검증하면 100% 통과로 보인다. 실제로 이렇게 놓친 사례가 있다.

- [ ] **중첩 모달 — 모달 안에서 여는 모달이 형제 위치에 렌더돼 있지 않은가?**
      iOS는 이미 present된 view controller 위로 root에서 또 present를 시도하면 두 번째를
      **조용히 무시**한다(에러 없음). Android는 별도 Dialog로 쌓여서 정상적으로 뜬다.
      → **AlarmApp 실제 사례(2026-08-03)**: `CycleRestControls`(N일 주기/휴식 팝업)가 진짜
      `<Modal>`인데, 그 안 📅 시작일 칩이 여는 `DateModal`(달력)은 베이스 화면에 있는
      **형제 Modal**이었다. iOS에서만 달력이 안 떴고, Android는 정상이라 발견이 늦었다.
      도입 커밋은 `fb59184`(2026-07-27) — 그 시점엔 이 전담반도 verify-fix도 없었다.
      **해결 패턴**: 여는 쪽 Modal이 `children` 슬롯을 받아 자기 `<Modal>` 트리 안
      (오버레이 `TouchableOpacity`의 **형제**로 — 안에 넣으면 배경 탭 닫기와 터치가 얽힌다)
      에서 렌더한다. 그리고 두 인스턴스가 겹치지 않게 바깥 인스턴스는 배타 마운트한다.
      **정적 검사 있음**: `./scripts/test-alarm-suite.sh --static`의
      "모달 안에서 여는 모달이 형제로 새지 않는지" 항목이 이 패턴을 잡는다. 모달 구조를
      건드렸으면 반드시 돌릴 것.
- [ ] **`onRequestClose` 누락** — Android는 하드웨어 back으로 네이티브 Dialog가 닫히는데
      JS의 `visible` 상태는 true로 남아 이후 동작이 어긋난다. iOS는 back이 없어 증상이
      아예 안 보인다. 모달을 새로 만들 때 항상 붙인다.
- [ ] **알림 액션/워치 연동** — iOS는 카테고리 옵션에 `customDismissAction: true`가 없으면
      단순 닫기 이벤트가 앱에 전달되지 않는다(`~/.claude/CLAUDE.md` 전역 규칙).

**검증 규칙**: 모달 계층·알림 액션을 건드린 수정은 **Android만 보고 통과 처리하지 말 것.**
iOS 시뮬레이터(또는 `폰`/`미니`)에서 해당 화면을 실제로 열어 스크린샷으로 확인한 뒤 완료 처리한다.
"Android에서 잘 되니 됐다"는 이 클래스의 버그에서 아무 근거가 못 된다.

## 절대 규칙 — 무조건 1:1 포팅하면 안 되는 것 (모든 프로젝트 공통)

- [ ] **이중 알람 시스템은 Android 전용, iOS로 포팅하지 않는다.**
      iOS는 Expo Notifications 하나로 충분(`~/.claude/CLAUDE.md` 전역 규칙).
      Android만 Doze 모드·배터리 최적화 때문에 `AlarmManager`를 추가로 쓴다. iOS에
      유사 네이티브 알람 모듈을 만들려는 시도는 하지 말 것 — Expo 로컬 알림으로
      충분하고 오히려 App Store 심사 리스크만 커진다. (자세한 구조는 alarm-logic
      전담반 참고.)
- [ ] **워치 연동 커스텀 액션 필수 옵션은 플랫폼마다 다르다.**
      iOS는 알림 카테고리 옵션에 `customDismissAction: true`를 반드시 설정해야 워치/배너
      스와이프 닫기에도 이벤트가 온다(`~/.claude/CLAUDE.md` 전역 규칙). Android는 이 옵션이
      필요 없다 — 그대로 옮기면 안 됨, 각 플랫폼 API 문서 기준으로 구현.

이 두 가지처럼 "기능은 같아야 하지만 구현 방식은 플랫폼마다 다르다"는 원칙을 항상
먼저 확인한 뒤 포팅 범위를 정한다.

## 작업 절차

1. **현재 프로젝트의 네이티브 코드 위치 확인**
   ```bash
   PROJECT_ROOT=$(pwd)
   find "$PROJECT_ROOT/android/app/src/main/java" -name "*.kt" -o -name "*.java" 2>/dev/null
   find "$PROJECT_ROOT/ios" -name "*.swift" -o -name "*.m" -o -name "*.h" 2>/dev/null | grep -v Pods
   ```
2. **변경/추가된 기능 파악**: 최근 커밋 또는 사용자가 지목한 기능이 어느 플랫폼
   네이티브 코드에 있는지 확인.
3. **이식 대상인지 판단**: 위 "절대 규칙"에 해당하면 포팅하지 않고 이유를 설명.
   해당 없으면 4번으로.
4. **플랫폼 비대칭 현황 파악**: 두 플랫폼 네이티브 디렉터리를 비교해서 한쪽에만
   있는 모듈(위젯, 커스텀 권한 등)을 찾는다. 프로젝트마다 다르므로 매번 새로 파악
   — 과거 조사 결과가 프로젝트 메모리에 있으면 참고하되 코드로 재확인.
5. **플랫폼별 동등 구현 설계**: 대상 플랫폼의 OS API로 같은 사용자 경험을 만드는
   방법을 먼저 찾는다.
6. **구현**: 대상 플랫폼 네이티브 코드 작성/수정. React Native 브릿지가 필요하면
   `Platform.OS` 분기가 있는 기존 파일 구조를 참고해 동일 패턴으로 추가.
7. **검증**: Android 변경이면 android-build 전담반, iOS 변경이면 ios-build
   전담반에 인계해 실기기 확인. 알람 관련 파일이면 alarm-test 전담반에도 위임.
8. **결과 기록**: 발견한 플랫폼 비대칭·포팅 완료 항목을 프로젝트 메모리에 남겨서
   다음 작업 때 다시 전체 스캔하지 않게 한다 (이 에이전트 파일 자체는 프로젝트
   무관이라 프로젝트별 현황을 적어두지 않는다 — 메모리에 기록).
